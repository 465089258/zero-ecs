# 单位与属性模块库设计

> 类别：设计
> 状态：草案
> 权威性：规范性
> 适用范围：基于 `@zero-ecs/game` 构建的角色、怪物、召唤物和可破坏物
> 最后更新：2026-07-25
> 上位文档：[架构宪法](./100-架构-架构宪法.md)
> 开发规范：[状态与行为开发规范](./210-规范-状态与行为开发.md)
> 模块规范：[可插拔 ECS 模块设计规范](./220-规范-可插拔ECS模块.md)
> 性能规范：[性能与分配模型](./230-规范-性能与分配.md)

本文先固定 `@zero-ecs/unit` 的代码边界、公共 API 和内部数据布局，不表示当前仓库已经提供
对应实现。第一版只处理“单位身份 + 数值属性 + 可消耗当前值”，不把伤害、Buff、装备、
技能、阵营关系或 AI 规则塞入基础库。

## 1. 定位

`@zero-ecs/unit` 是位于 `@zero-ecs/game` 上方的领域扩展：

```text
@zero-ecs/world          @zero-ecs/scheduler
          \              /
             @zero-ecs/game
                    │
             @zero-ecs/unit
       单位身份、属性目录、属性运行时
```

职责分为三部分：

- `Unit`：标识哪些 Entity 是单位，并保存稳定的单位种类、队伍和公共标志；
- `Attribute`：为 Entity 保存基础值、Modifier、最终值和可选的当前值；
- `UnitAttributeModule`：把目录、State、Service 和 System 安装进 Game。

属性不是 Component 类型。游戏允许内容模块在同一目录中增加任意属性；若把每个属性定义为
Component，会导致组件类型和 Archetype 组合随内容膨胀。单位身份仍是 Component，因为它
需要参与普通 ECS Query。

## 2. 非目标

第一版明确不提供：

- `takeDamage()`、暴击、护甲公式和元素克制；
- Buff 的持续时间、层数、驱散和光环传播；
- 装备栏、技能树、等级成长和经验值；
- 单位之间的敌我判定；
- 属性定义中的任意 JavaScript 求值闭包；
- 每个 Modifier 一个 Entity 或 Component；
- 在属性 API 内部直接调用 `World.spawn/despawn`；
- 跨属性派生公式图。

这些能力应在上层模块中组合属性请求。例如 Damage 模块计算伤害结果后调整 Health 当前值，
Status 模块拥有持续时间并在状态结束时删除自己的 Modifier。

## 4. 冷路径定义 API

### 4.1 属性定义

属性以对象 token 表示，业务 API 不暴露运行时数字 ID：

```ts
export interface AttributeDefinitionOptions {
    /** 跨包、存档和网络协议中稳定且唯一的名称。 */
    readonly key: string;
    readonly defaultBase?: number;
    readonly minimum?: number;
    readonly maximum?: number;
    /** 存在时，该属性同时拥有可消耗的 current 值。 */
    readonly current?: AttributeCurrentOptions;
}

export interface AttributeCurrentOptions {
    readonly initial?: "maximum" | number;
    readonly minimum?: number;
    readonly onMaximumChanged?: "clamp" | "preserve-ratio" | "preserve-deficit";
}

export interface AttributeDefinition {
    readonly key: string;
    readonly defaultBase: number;
    readonly minimum: number;
    readonly maximum: number;
    readonly current?: Readonly<Required<AttributeCurrentOptions>>;
}

export function defineAttribute(
    options: AttributeDefinitionOptions,
): AttributeDefinition;
```

示例：

```ts
export const Attack = defineAttribute({
    key: "combat.attack",
    defaultBase: 10,
    minimum: 0,
});

export const Health = defineAttribute({
    key: "combat.health",
    defaultBase: 100,
    minimum: 1,
    current: {
        initial: "maximum",
        minimum: 0,
        onMaximumChanged: "clamp",
    },
});
```

`Health` 的基础值和最终值表达生命上限，`current(entity, Health)` 表达当前生命。这样 Modifier
只改变上限，不会把“受到 10 点伤害”误建模成一个永久属性 Modifier。

### 4.2 属性目录

```ts
export class AttributeCatalog {
    constructor(definitions?: Iterable<AttributeDefinition>);

    add(...definitions: readonly AttributeDefinition[]): this;
    has(definition: AttributeDefinition): boolean;
    definition(key: string): AttributeDefinition | undefined;
    get size(): number;
}
```

Module 在 `build()` 中冻结目录。编译时按 `key` 排序后分配连续的内部 `AttributeId`，因此模块
注册顺序不影响布局、存档或确定性。重复 key 只有在引用同一 token 时才幂等；两个不同 token
使用同一 key 必须报错。

第一版限制属性数不超过 `65535`，内部 ID 使用 `Uint16Array`。所有默认值和边界必须为有限数，
且满足 `minimum <= defaultBase <= maximum`。

### 4.3 单位定义

单位定义只保存创建模板，不保存运行时状态：

```ts
export interface UnitAttributeBase {
    readonly attribute: AttributeDefinition;
    readonly value: number;
}

export interface UnitDefinitionOptions {
    readonly key: string;
    readonly attributes?: readonly UnitAttributeBase[];
    readonly flags?: number;
}

export interface UnitDefinition {
    readonly key: string;
    readonly attributes: readonly UnitAttributeBase[];
    readonly flags: number;
}

export function defineUnit(options: UnitDefinitionOptions): UnitDefinition;

export class UnitCatalog {
    constructor(definitions?: Iterable<UnitDefinition>);
    add(...definitions: readonly UnitDefinition[]): this;
    definition(key: string): UnitDefinition | undefined;
}
```

单位目录同样按 key 编译成内部 `UnitKindId`。模板只覆盖目录中的默认基础值；没有覆盖的属性
使用 `AttributeDefinition.defaultBase`。

## 5. 公共运行时 API

### 5.1 单位创建

```ts
export interface SpawnUnitOptions {
    readonly team?: number;
    readonly flags?: number;
    readonly attributes?: readonly UnitAttributeBase[];
}

export interface IUnitService {
    spawn(definition: UnitDefinition, options?: SpawnUnitOptions): Entity;
    despawn(entity: Entity): void;
    isUnit(entity: Entity): boolean;
}

export class UnitService extends Service implements IUnitService {
    // 实现不从接口泄漏 State、Commands 或内部 Component。
}
```

`spawn()` 立即通过 `Commands.spawn()` 预留并返回 Entity，但单位 Component 和属性集在
`Update.post` 的 Commands/Structure 边界提交。调用方可对返回的 Entity 继续提交 Position、
模型或 AI Component；同一提交批次由 Game 合并成一次最终迁移。

`despawn()` 同时请求删除属性集和 Entity。其他模块若绕过 UnitService 直接销毁 Entity，公开
读取会立即以 `World.valid(entity)` 拒绝旧句柄，内部清理 System 在下一次扫描时回收残留属性。
因此残留不会被复用到相同 slot 的新版本 Entity，但可能多保留至下一个清理批次。

### 5.2 属性读取与请求

```ts
export const AttributeModifierOperation = Object.freeze({
    Flat: 0,
    Increased: 1,
    More: 2,
} as const);

export type AttributeModifierOperation =
    (typeof AttributeModifierOperation)[keyof typeof AttributeModifierOperation];

export interface AttributeModifier {
    readonly attribute: AttributeDefinition;
    readonly operation: AttributeModifierOperation;
    readonly value: number;
    /** 用于诊断、批量移除和存档关联；不参与公式。 */
    readonly source?: Entity;
}

declare const ModifierHandleBrand: unique symbol;
export type ModifierHandle = number & {
    readonly [ModifierHandleBrand]: "ModifierHandle";
};

export interface IAttributeService {
    has(entity: Entity): boolean;
    base(entity: Entity, attribute: AttributeDefinition): number | undefined;
    value(entity: Entity, attribute: AttributeDefinition): number | undefined;
    current(entity: Entity, attribute: AttributeDefinition): number | undefined;

    setBase(entity: Entity, attribute: AttributeDefinition, value: number): void;
    addBase(entity: Entity, attribute: AttributeDefinition, amount: number): void;

    addModifier(entity: Entity, modifier: AttributeModifier): ModifierHandle;
    removeModifier(handle: ModifierHandle): void;
    removeModifiersFrom(source: Entity): void;

    setCurrent(entity: Entity, attribute: AttributeDefinition, value: number): void;
    addCurrent(entity: Entity, attribute: AttributeDefinition, amount: number): void;
}

export class AttributeService extends Service implements IAttributeService {
    // 写操作进入可复用请求队列；读取返回上一次 apply 后的已提交值。
}
```

`current/setCurrent/addCurrent` 只接受声明了 `current` 的属性，否则抛出 `TypeError`。
所有写入拒绝 `NaN` 和无穷值。无效 Entity、未挂接属性集的 Entity 或不属于当前目录的定义
都在冷边界明确报错，不静默创建数据。

写操作不立即改变可读值，而是进入 `AttributeRequestState`。这带来统一的单 Tick 顺序、
可合并写入和稳定高水位复用。需要同 Tick 观察结果的系统放在 `AttributeSystemSet.Apply`
之后；生产请求的系统放在它之前。

### 5.3 Modifier 公式

对同一个 Entity 和 Attribute：

```text
flat      = Σ Flat.value
increased = Σ Increased.value
more      = Π (1 + More.value)

raw   = (base + flat) × max(0, 1 + increased) × more
value = clamp(raw, definition.minimum, definition.maximum)
```

`Increased: 0.2` 表示所有 Increased 相加后增加 20%；`More: 0.2` 表示独立乘以 1.2。
`More.value` 必须大于 `-1`。Modifier 按稳定 Handle 顺序求积，避免删除和重插造成未定义顺序。

第一版不提供 Override 和 priority。两者组合后很容易让最终值依赖模块注册顺序；需要覆盖时，
上层系统应设置基础值或用一个明确拥有最终决策权的派生模块。

## 6. ECS Component 与只读 Query

内部单位 Component 建议布局：

```ts
enum UnitField {
    Kind,
    Team,
    Flags,
    Revision,
}

class UnitStorage implements Component<UnitField> {
    readonly [UnitField.Kind] = Types.U16;
    readonly [UnitField.Team] = Types.U16;
    readonly [UnitField.Flags] = Types.U32;
    readonly [UnitField.Revision] = Types.U32;
}
```

根入口不导出 `UnitStorage`，只导出只读投影：

```ts
export enum UnitViewField {
    Kind,
    Team,
    Flags,
    Revision,
}

export interface UnitViewData {
    readonly [UnitViewField.Kind]: typeof Types.U16;
    readonly [UnitViewField.Team]: typeof Types.U16;
    readonly [UnitViewField.Flags]: typeof Types.U32;
    readonly [UnitViewField.Revision]: typeof Types.U32;
}

export const UnitView =
    defineQueryProjection<UnitViewData>(UnitStorage, "UnitView");

export const UnitQuery = QueryType.from(With(UnitView));
```

属性不提供“每个值一个 Query 列”的伪投影。批量战斗系统先遍历自身 Query，再用
AttributeService 的数字 Entity 读取属性。后续基准若证明逐实体调用成为瓶颈，再增加显式的
批量只读游标 API，而不是暴露内部 State。

## 7. 内部 State 与数据布局

### 7.1 AttributeState

`AttributeState` 是权威模拟状态，使用按 Entity slot 分页的稀疏索引和稠密单位行：

```text
sparse page[entityIndex] -> denseRow + 1
denseEntities[denseRow]  -> 完整 Entity（含版本）

cell = denseRow × attributeCount + attributeId

base[cell]       Float64Array
effective[cell]  Float64Array
current[cell]    Float64Array
dirty[cell]      Uint8Array
modifierHead[cell] Int32Array
```

稀疏命中后必须比较 `denseEntities[row] === entity`，不能只比较 slot。删除单位使用
swap-remove；被移动行的 sparse 索引和 Modifier 所属行同步更新。

选择稠密矩阵的理由：

- 目录在构建后固定，AttributeId 连续；
- 单位通常反复读取一组共同的战斗属性；
- 最终索引是一次乘加，没有每次读取 Map 或对象分配；
- 属性数和单位数的内存成本可直接预测。

若项目拥有数千种属性但每个单位只有极少属性，应另建稀疏属性扩展，不能让第一版同时维护
两套热路径。

### 7.2 ModifierStorage

Modifier Handle 使用“slot + generation”，不能把数组下标直接作为永久 Handle。每个有效
Modifier slot 保存：

```text
generation / ownerEntity / attributeId / operation / value / source / next
```

`modifierHead[cell]` 和 `next[slot]` 形成每个属性单元的链表。新增或删除只标记对应 cell dirty；
Apply System 只重算 dirty cell，不全量扫描全部 Modifier。

### 7.3 AttributeRequestState

请求队列按操作类型保存 SoA 数组和 `used` 游标：

```text
operation / entity / attributeId / value / modifierHandle / source
```

稳定高水位下只覆盖已有数组元素。Apply 后把 `used` 归零，不清空容量。删除同 Tick 尚未生效
的 Modifier Handle 时，在合并阶段直接取消新增请求。

## 8. System 顺序

```ts
export const AttributeSystemSet = Object.freeze({
    Apply: new SystemSet(Update.fixed, "attribute:apply"),
    Cleanup: new SystemSet(Update.last, "attribute:cleanup"),
});
```

模块注册两个系统：

```text
Update.fixed
  属性/Modifier/当前值请求生产者
      ↓ before AttributeSystemSet.Apply
  applyAttributeRequestsSystem
      ↓ after AttributeSystemSet.Apply
  伤害结果、死亡判断、技能编译等消费者

Update.last
  cleanupInvalidAttributeOwnersSystem（分片清理）

Update.post
  Commands → Structure
```

Apply 的确定顺序为：

1. 按提交顺序合并基础值写入；
2. 安装和删除 Modifier；
3. 重算 dirty 最终值；
4. 根据 `onMaximumChanged` 调整 current；
5. 合并并应用 current 写入；
6. 清空请求游标。

同一 Tick 多次 `setBase` 取最后一次，`addBase` 在最终 `setBase` 后累加；`setCurrent` 同理，
随后应用全部 `addCurrent`。这些规则必须由单元测试固定，不能依赖偶然的循环实现。

## 9. Module 代码草案

```ts
export interface UnitAttributeModuleOptions {
    readonly attributes: AttributeCatalog;
    readonly units: UnitCatalog;
    readonly cleanupBudget?: number;
}

export class UnitAttributeModule implements Module {
    constructor(private readonly options: UnitAttributeModuleOptions) {}

    build(builder: GameBuilder): void {
        const attributes = this.options.attributes.compile();
        const units = this.options.units.compile(attributes);

        builder
            .addResource(CompiledAttributeCatalog, attributes)
            .addResource(CompiledUnitCatalog, units)
            .addState(AttributeState)
            .addState(AttributeRequestState)
            .addService(AttributeService)
            .addService(UnitService);

        builder.addSystem(applyAttributeRequestsSystem, {
            inSet: AttributeSystemSet.Apply,
        });
        builder.addSystem(cleanupInvalidAttributeOwnersSystem, {
            inSet: AttributeSystemSet.Cleanup,
        });
    }
}
```

实际实现中 `compile()` 和两个 Compiled token 可以保持包内，不进入根入口。Module 只安装
依赖，不保存到 Game，也不拥有运行时生命周期。

使用示例：

```ts
const attributes = new AttributeCatalog([Attack, Health]);
const units = new UnitCatalog([
    defineUnit({
        key: "monster.wolf",
        attributes: [
            { attribute: Attack, value: 12 },
            { attribute: Health, value: 80 },
        ],
    }),
]);

builder
    .addModule(new CommandModule())
    .addModule(new UnitAttributeModule({ attributes, units }));

// System 或宿主入口：
const wolf = unitService.spawn(units.definition("monster.wolf")!, { team: 2 });
attributeService.addModifier(wolf, {
    attribute: Attack,
    operation: AttributeModifierOperation.Increased,
    value: 0.25,
    source: equipmentEntity,
});
attributeService.addCurrent(wolf, Health, -20);
```

`UnitAttributeModule` 依赖 Commands。第一版应在构建或初始化时对缺失依赖给出明确诊断；不要
在包内偷偷安装 `CommandModule`，以免 Module 是否存在变得不可观察。

## 11. 测试与验收

实现阶段至少需要以下测试：

### 11.1 目录与构建

- 属性和单位 key 与注册顺序无关；
- 重复 key、非法边界、非有限数和未知属性失败；
- 目录编译后不可修改；
- 缺少 CommandModule 时产生清晰错误；
- 根入口不导出 State、Storage 和内部 System。

### 11.2 单位生命周期

- spawn 返回有效预留 Entity，下一 Tick 可由 UnitQuery 观察；
- 同一 Entity 的额外 Component 与 UnitStorage 只迁移一次；
- UnitService.despawn 同时删除属性；
- 绕过 UnitService 销毁后，旧版本 Entity 不可读；
- slot 复用不会继承旧版本 Entity 的属性或 Modifier。

### 11.3 属性规则

- Flat、Increased、More 和 clamp 公式；
- Modifier 删除、重复删除、失效 Handle 和 generation 回绕隔离；
- 同 Tick set/add 合并顺序；
- current 的 clamp、preserve-ratio 和 preserve-deficit；
- 调低上限、负治疗、过量治疗和未声明 current；
- `removeModifiersFrom(source)` 只删除匹配来源。

### 11.4 性能与分配

- 稳定单位数和 Modifier 高水位下 Apply 不逐请求创建对象；
- 只重算 dirty cell；
- 清理使用预算分片，不每 Tick 全量扫描 World；
- Node JIT、`--jitless` 和浏览器分别比较逐实体读取与批量游标候选方案；
- 基准至少覆盖 1 万单位 × 16 属性、10% dirty，以及大量短期 Modifier 两类负载。

## 12. 实施顺序

1. 建立 `packages/unit`、定义 token、两个目录及目录测试；
2. 实现 AttributeState 稠密矩阵和 Entity 版本隔离；
3. 实现请求队列、公式、current 策略和 Modifier Handle；
4. 实现 UnitStorage、只读投影、spawn/despawn 与延迟提交；
5. 增加清理 System、公共入口和 package-boundary 测试；
6. 把 shooter-zombie 示例的固定 Health 模块迁移为使用 `@zero-ecs/unit`；
7. 运行 typecheck、test、build、no-JIT smoke 和专项基准后再把本文状态改为“已评审”或
   “实施中”。

## 13. 仍需评审的问题

- `Team` 第一版使用 `U16` 数字，还是改为可版本校验的 Entity；
- AttributeService 的逐实体读取在目标游戏规模下是否足够，何时增加批量游标；
- 单位目录是否需要稳定的外部数值 ID，还是只承诺稳定 key；
- 快照系统落地后，Modifier source Entity 和 Handle generation 的序列化格式；
- 是否在第二版加入编译后的跨属性派生图，以及如何检测依赖环。
