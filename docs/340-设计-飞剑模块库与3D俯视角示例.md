## 1. 定位与依赖

飞剑能力作为独立领域扩展包存在，不成为 World、Scheduler、Game 之后的第四个核心层：

```text
@zero-ecs/world          @zero-ecs/scheduler
          \              /
             @zero-ecs/game
                    ↑
             @zero-ecs/math
                    ↑
            @zero-ecs/motion
                    ↑
       @zero-ecs/flying-sword
                    ↑
       examples/flying-sword
```

约束如下：

- 飞剑包只依赖 `@zero-ecs/game`、`@zero-ecs/math/3d` 和
  `@zero-ecs/motion/3d` 的公共入口，不直接导入 World 或 Scheduler 包。
- Math 提供位置、历史位置、速度和方向等通用 ECS 数学事实；Motion 提供领域无关的
  最终目标追踪与积分；飞剑包不重复实现这些基础能力。
- 三个核心包不得导入或重导出飞剑包。
- 飞剑包只负责权威 3D 空间数据和领域运行时，不定义相机、视口、2D 投影、屏幕坐标、
  深度渲染队列或绘制层。
- 素材编号、视觉配方和渲染组件属于内容层或表现层，不进入飞剑领域组件。
- 飞剑包不导入 Canvas、DOM、浏览器 API 或表现模块。
- 示例只使用飞剑包公开入口，不访问内部物理存储。
- 飞剑包独立声明版本和公共 API，不参与核心三包的职责划分。

当前公开入口：

```text
@zero-ecs/flying-sword
```

## 2. 世界坐标

数据层使用右手 3D 世界坐标：

```text
+X：角色右方
+Y：上方高度，地面通常为 Y = 0
+Z：角色前方纵深
```

ECS 只保存权威世界坐标、上一固定 Tick 坐标、速度和朝向，不保存 `screenX`、
`screenY` 等表现数据。

## 3. 基础领域身份

每一把实际飞剑是持久 Entity；每个控制组也拥有 Entity 身份。一名角色可以拥有多个
控制组，一把剑同一时刻最多属于一个控制组。

当前基础设施已经实现：

- `FlyingSwordGroupStorage`：控制组内部可写物理存储。
- `FlyingSwordMemberStorage`：只保存控制组和槽位的领域身份。
- `FlyingSwordFlightStorage`：只保存最大速度和基础加速度。
- `FlyingSwordFormationGoal3Storage`：编队系统产生的领域目标。
- Math 的 `Position3Type`、`PreviousPosition3Type`、`Velocity3Type` 和
  `Direction3Type`：通用 3D 运动事实。
- Motion 的 `MoveTowards3Type`：编队与技能制导归并后的最终运动输入。
- `FlyingSwordSkillActionStorage`：技能预留期间才存在的动作组件。
- `FlyingSwordContactWindowStorage`：只有攻击接触窗口开放时才存在的标记组件。
- `FlyingSwordGroupView`、`FlyingSwordView`：公开只读 QueryProjection。
- `FlyingSwordGroupQuery`、`FlyingSwordQuery`、`FlyingSwordActionQuery` 和
  `FlyingSwordContactQuery`：宿主集成、表现与战斗集成所需的公共只读查询。
- `FlyingSwordService`：创建控制组、创建飞剑和提交战术指令。

内部 Storage 不属于包公共入口；`FlyingSwordQuery` 中的 Math 数据也通过只读投影暴露，
调用方不能借助飞剑公共查询修改飞剑数据。

## 4. 固定帧运行时

`FlyingSwordModule` 要求宿主同时安装 `CommandModule`、`TimeModule` 和
`Motion3Module`。宿主 Integration 在固定 Tick 中读取自身角色位置，并通过
`FlyingSwordService.setCenter` 更新控制组中心。

当前基础系统顺序：

```text
Request
→ Control
→ Skill
→ Formation
→ Guidance
→ MotionSystemSet.Integrate3
→ Contact
→ Cleanup
```

当前已经实现完整的基础管线：

- 浏览器或宿主输入只写请求队列。
- Request System 在固定 Tick 应用控制组指令。
- 宿主 Integration 在 Control 前同步控制组中心；飞剑包只读取自身组数据生成快照，
  不通过飞剑专用空间适配器反向读取宿主组件。
- Formation 只写领域编队目标，Guidance 把空闲编队或活跃技能轨迹归并为
  `MoveTowards3Type`。
- 通用 Motion System 以最终目标、速度和加速度限制更新 Math 运动组件。
- Skill System 为技能动作预留飞剑；Formation System 生成默认槽位，Guidance System
  使用技能目标覆盖最终运动目标。
- 技能开始时在同一 Commands 提交批次为选中飞剑添加动作组件；Launch 末段开放接触窗口，
  转入 Return 时关闭；重新入阵后移除动作组件。结构迁移发生在既定提交边界，不在活跃
  Query 迭代中直接修改 World。
- Contact System 推进飞剑技能阶段，Cleanup System 在重新入阵后释放组级动作记录。
- 控制组通过 `verticalAmplitude` 和 `verticalSpeed` 定义 Y 轴高度波；各剑按阵位错开
  相位，形成连续的立体升降，而不是表现层伪造的屏幕抖动。
- Motion 每次积分前把 `Position3Type` 复制到 `PreviousPosition3Type`，供显示帧插值。

Formation、Guidance、Contact 和 Cleanup 既是对外稳定系统锚点，也已用于首个
“御剑诀·穿云”垂直切片。完整剑阵编译、轨迹扫掠和接触事实缓冲仍在后续阶段实现。

## 5. 宿主集成边界

飞剑库不规定“控制组中心来自哪个实体或模块”，也不读取宿主自定义 Transform。宿主系统
负责把角色、载具、召唤物或服务器同步位置投影为控制组中心：

```ts
flyingSwords.setCenter(group, center);
```

其中 `center` 是宿主复用的 `ReadonlyVector3` 输入对象；该调用只写飞剑请求队列，在固定
Tick 的 Request 阶段生效。当前示例的修士直接复用
Math 的 `Position3Type`，由 `synchronizeFlyingSwordGroupCenterSystem` 批量读取并同步；
真实游戏可以从角色模块、网络快照或其他来源完成同一映射。飞剑包不再发布
`integration` 子路径或 `FlyingSwordSpatialService`。

## 6. 相机位置与角度

默认相机位于角色后上方，朝角色前方与下方观察。示例使用 `45°` 水平偏角，使世界 X/Z
方格通过真实相机投影自然形成菱形网格；相机仍位于角色后侧半空间。

相机视线与地面夹角定义为：

```text
0°  ：水平观察
90° ：垂直俯视
```

相机类的通用默认角度为 `50°`；当前飞剑示例为了加强纵深、菱形地面和飞剑高度表现，
显式使用 `30°`。推荐可调范围为 `30°～55°`。30° 时：

```text
高度屏幕贡献 cos(30°) ≈ 0.866
纵深屏幕贡献 sin(30°) = 0.5
```

较低夹角会增强飞剑高度和阴影分离，但压缩地面纵深；实际产品应根据角色遮挡和地图
可读性在上述范围内校准。

## 7. 投影与排序

表现层必须从同一组相机基向量同时计算屏幕位置和相机空间深度。当 `yaw = 0` 时：

```ts
cameraRight   = (1, 0, 0);
cameraUp      = (0, cosθ, sinθ);
cameraForward = (0, -sinθ, cosθ);
```

对相机目标的相对坐标 `d = position - cameraTarget`：

```ts
screenX = viewportCenterX + dot(d, cameraRight) * zoom;
screenY = viewportCenterY - dot(d, cameraUp) * zoom;
depth   = dot(d, cameraForward);
```

不得使用世界 Z 或投影后的 screenY 代替 depth。相机转向后 X 也会影响深度，高度 Y
始终影响遮挡关系。

Canvas 使用画家算法：

```ts
layer ascending
→ depth descending
→ subOrder ascending
→ stableId ascending
```

`cameraForward` 指向场景，所以 depth 越大越远；远处对象先绘制。`stableId` 是明确的
平局键，防止同深度对象逐帧抖动。

以下表现设施只属于 `examples/flying-sword/src/presentation`，不属于飞剑 npm 包：

- `TopDownOrthographicCamera`
- `DepthRenderQueue`
- `compareDepthRenderItems`
- `DemoRenderLayer`

示例的 `yaw = 45°` 只改变相机基向量，不使用单独的假菱形坐标。网格、飞剑、阴影、
点击反投影和深度排序始终共用同一个相机。

## 8. 排序锚点

每个渲染原语必须明确排序锚点：

- 飞剑：剑身中点。
- 飞剑阴影：把剑身两端沿世界 Y 轴投影到 `Y = 0`，使用投影后剑身中点排序；复用飞剑
  原始 PNG 的 Alpha 轮廓，以黑色和半透明绘制，从而完整保留剑身、剑尖和剑格，不能
  另画简化轮廓或退化为圆点。
- 角色立绘：脚底。
- 命中特效：3D 接触点。
- 剑光和轨迹：拆分后的短线段中点。

长轨迹不能作为单一对象排序，否则一条轨迹同时跨越近处和远处时无法得到正确遮挡。

## 9. 示例

`examples/flying-sword` 当前展示：

- 一个持有 Math 通用 3D 运动组件的修士 Entity。
- 修士通过 `MoveTowards3Type` 接收鼠标左键的 X/Z 目标，由 Motion 固定 Tick 推进位置；
  示例自有的瞬态移动标记只表达“当前有角色移动命令”。
- 一个控制组和多把飞剑 Entity。
- 飞剑在 XZ 平面环绕，并在 Y 轴上保持飞行高度。
- 飞剑沿 Y 轴以错位相位连续升降；集中时收敛高度幅度，召回时降低高度和波动。
- 固定 60 Hz 模拟和 requestAnimationFrame 插值表现。
- 飞剑、角色和阴影的分层及相机深度排序。
- 世界 X/Z 方格在 45° 水平偏角下投影为菱形背景网格。
- 示例内容组件 `FlyingSwordVisualType` 按视觉编号选择青玉、赤金、寒铁或紫电像素飞剑
  素材，按投影后的剑身方向旋转；
  透视缩短只作用于素材的本地剑身轴，垂直于剑身的像素厚度保持稳定，禁止随转向同时缩放
  两个轴；Canvas 关闭图像平滑以保持像素边缘，素材未加载时才回退到线段。
- 鼠标左键经过地面反投影后设置角色移动目标，相机使用插值后的角色坐标连续跟随。
- 鼠标右键施放“御剑诀·穿云”；飞剑先在角色周围聚剑，再分波沿连续弧线升空、转向
  并俯冲贯穿目标，自动归剑并恢复环绕。
- 空格恢复环绕，R 切换召回指令。
- 显示角色、集火目标 XYZ 和当前最近、最远相机深度。

示例中的视觉组件、相机、2D 投影、反投影、裁剪、深度队列、Canvas、DOM 和输入均不
进入飞剑包。示例通过飞剑只读投影与自身视觉组件组成表现查询，再在表现阶段计算 2D
结果。

Canvas2D 后端只加载 128 像素宽的运行素材；高分辨率原图不进入浏览器产物。黑色 Alpha
阴影和颜色光晕在图片加载后一次性烘焙，稳定帧不执行 `filter` 或 `shadowBlur`。相机屏幕
粗裁剪发生在端点投影和入队之前；背景底色使用缓存 Canvas。相机跟随角色后，地面网格
必须保持世界坐标锚定，因此每帧只构造一条批量 Path 并统一描边，不为每根网格线单独
提交绘制。状态文本降低更新频率。像素风画布固定使用 DPR 1，避免 DPR 2 带来的四倍
填充面积。
