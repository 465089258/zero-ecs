它不重新定义三库职责；发生冲突时以架构宪法和专项设计为准。

## 1. 当前基线

截至 2026-07-23，以下迁移已经完成：

- World 使用局部 Chunk 版本，删除全局 Chunk layout version。
- Query 按匹配 Archetype 局部同步 Chunk。
- Archetype 提供默认值为 `0` 的 `spareChunkLimit` 机制。
- Scheduler 删除无效 Builder 标识，使用 Handle 对象身份校验归属。
- Scheduler runner 已在构建冷路径编译。
- Scheduler 已固定空 SystemSet 语义并提供真实环路诊断。
- `EntityTransaction` 和 `Migrations` 保持 Game 包私有实现。

当前工程验证：

- `npm run test`：151 项测试全部通过。
- `npm run verify:release`：通过。
- 验证环境为 Windows、Node `v26.0.0`。

上述验证只证明当前工程门禁通过，不替代固定 Node 22 和 Chromium 的正式性能门槛。

## 2. 总体执行顺序

```text
P0 Commands 提交控制面（已完成）
    ↓
P0 DevProfiler 实例隔离与 Chunk 诊断（已完成）
    ↓
P1 Game 根入口收缩（已完成）
    ↓

```

World、Scheduler、Game 的性能候选必须保持独立，不把多个阶段混成一次 A/B candidate。

## 3. P0（已完成）：收紧 Commands 提交控制面

### 3.1 问题

迁移前 `Commands` 运行时对象暴露：

- `flush()`；
- pending EntityTransaction 数量和实体读取；
- Flush extension 注册与移除。

即使部分方法通过 `@internal` 从声明产物中移除，JavaScript 运行时仍可调用。业务 System
因此可能制造第二个提交边界，Hierarchy 等可选模块也直接依赖 Commands 管理接口。

### 3.2 目标

- 稳定业务 API 只保留 `command()`、`entity()`、`spawn()` 和明确允许的维护能力。
- `flush/collect/apply` 只能由内建提交 System 触发。
- pending 观察和 Flush extension 保持包内协议。
- 不新增 World 依赖或通用 Scheduler 领域逻辑。
- 不为热路径增加仅用于隐藏 API 的 Service facade 或动态分派层。

### 3.3 实施边界

优先考虑包内非导出 token、模块私有协议或同文件内建执行器。Hierarchy 必须继续能够在普通
Command 执行后、Migrations collect 前扩展级联 despawn，但该协议不能进入公共包入口。

### 3.4 完成定义

- 公共类型和根入口无法取得提交控制协议。
- 普通业务代码不能调用 `Commands.flush()`。
- 内建提交 System 仍然只产生一个既定提交边界。
- Hierarchy 级联 despawn、命令重入、错误处理和回收测试通过。
- package-boundary 测试明确断言内部控制面不可导入。
- `npm run verify:release` 通过。

### 3.5 完成结果

- 使用不从包入口导出的唯一 symbol 连接内建提交 System、Commands 和 Hierarchy。
- `Commands` 运行时对象不再存在字符串形式的 flush、扩展注册和 pending 读取属性。
- `CommandFlushContext` 只提供 pending 观察和稳定 `ICommands`，扩展不能自行 flush。
- 稳定普通命令 API 采用 `command()`。
- 已增加运行时控制面缺失断言和深路径包边界断言。

## 4. P0（已完成）：DevProfiler 实例隔离与 Chunk 诊断

### 4.1 问题

迁移前 DevProfiler 修改全局 `Scheduler.prototype.run`，并使用静态共享统计表。一个 Game 的
调试行为会影响同进程的其他 Game 和独立 Scheduler，不满足实例隔离。

迁移前内存报告只汇总实体数和分配字节，未覆盖 Chunk 生命周期改造所需诊断。

### 4.2 目标

- 采样只属于目标 Game 实例。
- 不修改 Scheduler prototype。
- 不在 Scheduler 默认生产路径加入 profiler 分支。
- 每个 profiler 独立持有统计数据和释放状态。
- 内存报告补充逻辑 Chunk、物理 Chunk、spare Chunk、限制值和填充率。

### 4.3 完成定义

- 同进程两个 Game 的统计彼此隔离。
- 独立 Scheduler 不受 Game profiler 影响。
- 重复 dispose 安全，不需要恢复全局 prototype。
- 未启用 profiler 时 Scheduler 热路径与当前生产路径一致。
- 空 Archetype、部分填充、满 Chunk 和 spare Chunk 报告测试通过。
- `npm run verify:release` 通过。

### 4.4 完成结果

- 只包装目标 Game 所属 Scheduler 的实例方法，不修改 Scheduler prototype。
- 同一 Game 的多个 profiler 独立统计，可按任意顺序重复释放。
- 未启用 profiler 时 Scheduler 和 Game 执行路径不变。
- 内存报告增加逻辑/物理/spare Chunk、限制值、填充率和汇总。
- 已覆盖多 Game、独立 prototype、多个 profiler、空/部分/满/spare Chunk 测试。

## 5. P1（已完成）：收紧 Game 根入口

### 5.1 问题

迁移前 Event、Time、Timer、Random、Hierarchy 和 Pool 已经具有独立子路径，但 Game
根入口仍然重导出这些可选 Feature。

### 5.2 目标

- 根入口只保留核心组合 API 和真正高频的公共声明。
- 可选 Feature 优先从各自子路径导出。
- 内部 State、池实现、提交 System 和存储对象不得进入根入口。
- Game 可以继续重导出常用 World API，但不得暴露 World advanced 存储实现。

### 5.3 实施步骤

1. 建立当前导出清单和目标导出清单。
2. 审查示例和测试中的根入口使用。
3. 将可选 Feature 使用迁移到子路径。
4. 收缩根入口。
5. 扩展 package-boundary 和类型导出断言。
6. 更新 API 参考和示例。

### 5.4 完成定义

- 根入口导出快照经过评审并固定。
- 所有可选 Feature 子路径可以独立导入。
- 示例不再依赖被移除的根入口导出。
- 深层内部路径继续被 package exports 阻止。
- `npm run verify:release` 通过。

### 5.5 完成结果

- Game 根入口已移除 Event、Time、Timer、Random、Hierarchy 和 Pool 重导出。
- 源码消费者、测试、benchmark 和示例已迁移到独立子路径。
- package-boundary 对全部可选根导出建立显式否定断言。
- 公共类型测试验证 Timer、Hierarchy 和 Pool 不能从根入口导入。

## 6. P2（已完成）：统一事务可见性文档

所有现行文档统一使用以下语义：

- 当前局部 `EntityTransaction` 内支持 read-your-writes。
- 不同事务在 collect 前彼此隔离。
- Query 在结构提交前看到旧 World。
- 每个 Migrations collect/apply 批次中，每个 Entity 最多发生一次最终迁移。

不得把上述语义简写为没有边界的“同帧可见”或“每帧最多迁移一次”。历史文档保留原始叙述
时，必须明确其历史性并链接当前规范。

完成条件是现行架构、设计、API 和开发规范中不存在歧义表述；历史归档不再被现行文档作为
事实来源。

现行架构和 API 文档已经统一到上述四条语义；历史开发计划保持历史归档，不再作为当前
事务语义来源。

## 7. P1 发布门槛：正式性能验证（待固定环境）

该阶段在 P0 和根入口迁移冻结后执行，不对即将继续变化的构建采集正式结论。

### 7.1 核心门槛

- 固定完整 Node 22 patch 版本。
- baseline 和 candidate 使用相同运行时与生产构建配置。
- 先执行独立进程 A/A paired 校准。
- 再执行 A/B、B/A 交替的 paired comparison。
- 正常 JIT 和 `--jitless` 分别报告。
- 保存原始 round 数据、环境、提交和构建信息。

### 7.2 发布候选门槛

- 固定完整 Chromium/V8 版本。
- 独立浏览器实例运行 baseline 和 candidate。
- 分别覆盖主线程连续计算和 `requestAnimationFrame` 帧调度。
- 声明 Worker 支持时增加 Worker 连续计算。

所有阈值、场景和统计方法以
[性能与分配模型](./230-规范-性能与分配.md)为准。

### 7.3 当前执行记录

2026-07-23 已完成：

- `npm run bench`：Node `v26.0.0` 单构建 smoke 全场景通过；
- `node benchmarks/compare.mjs --baseline-root . --candidate-root . --profile smoke`：
  A/A paired 控制器全场景通过；
- smoke 结果明确为 `approvalEligible: false`，不用于批准性能候选。

正式门槛尚未执行，当前环境只有 Node `v26.0.0`，没有固定 Node 22 patch 可执行文件；仓库也
没有冻结 baseline/candidate 构建目录和 Chromium 连续计算/rAF benchmark harness。准备这些
条件后，必须按 7.1 和 7.2 重新采集，不能用上述 smoke 替代。

## 8. P2：结构变化 Query

[Query 结构变化查询设计](./320-设计-Query结构变化查询.md)已经评审但尚未实施。它属于新增
能力，不计入当前 Game 控制面迁移的完成条件。

实施必须拆为独立阶段：

1. Q1：增加 `Added`、`Removed`、`Before` AST 和类型推导。
2. Q2：增加 World 按需结构变化记录和按 Entity 合并。
3. Q3：编译 Dense 或 StructuralChange 查询计划。
4. Q4：集成 Game 提交与下一 Tick 可见性。

Q4 依赖 Commands 提交控制面已经稳定。每个阶段需要独立测试；World 记录和查询热路径变更
需要独立性能 candidate。

## 9. P3：Game 自适应 spareChunkLimit

Game 根据迁移波动自动调整 `spareChunkLimit` 是延期候选，不属于 World 局部版本和默认
Chunk 回收机制的完成条件。

只有正式 churn 数据证明重复物理 Chunk 创建具有实际成本后才进入设计和实施。实施前必须
另外确定：

- 固定用户配置与自适应配置的独立存储；
- 配置优先级；
- 迁移触达和波动状态的记录位置；
- 降级与内存压力恢复规则；
- 独立 benchmark 和默认启用条件。

第一版不得默认启用自适应策略。
